# 自作アプリ共通デバッグ標準 v1

この文書は、Codex / ChatGPT を使って自作アプリを継続的に総合デバッグするための共通基準です。
プロジェクト固有の仕様は `docs/SPEC.md` とそこから参照される正本を優先し、この文書は仕様を変更しません。

## 1. デバッグ開始条件

ユーザーが「総合デバッグして」「デバッグして」「一通りテストして」など、アプリ全体の品質確認を依頼した場合は、原則として次の順で進めます。

1. `AGENTS.md`
2. `docs/SPEC.md`
3. `docs/STATUS.md`
4. プロジェクト固有の仕様書
5. `docs/DEBUG_STANDARD.md`
6. `docs/DEBUG_MATRIX.md`
7. 既存テスト、build / typecheck / lint / CI 設定

`docs/DEBUG_MATRIX.md` が未整備なら、実装と仕様からそのアプリ固有のケースを先に追加してから検証します。

## 2. 共通テスト分類

### A. 正常系
主要フローが仕様どおり最後まで完了する。

### B. 異常系
空入力、不正入力、保存失敗、読込失敗、API失敗、不正レスポンスなどで壊れない。

### C. 境界値
0件、1件、2件、多数、最小値、最大値、端数、同値、非常に大きい値などを確認する。

### D. 状態遷移
入力後の条件変更、戻る、画面切替、再実行、保存後の再利用、再読み込みを確認する。

### E. 誤操作・連続操作
二重クリック、連打、同じ項目の追加削除、途中キャンセル、素早い画面移動を確認する。

### F. 永続化
localStorage、DB、ファイル、履歴、保存済みデータが再読み込み後も仕様どおり扱われる。

### G. 外部依存
API、位置情報、地図、認証、外部ストレージ等について、成功・拒否・失敗・遅延・空結果・不正応答を確認する。

### H. UI / 端末
主要スマホ幅、PC幅、長文、スクロール、ソフトキーボード、横はみ出し、CTAの重なり、キーボード操作を確認する。

## 3. ベースライン確認

修正前に、プロジェクトで利用できる検証コマンドを特定して実行します。

例:

- unit / integration test
- typecheck
- lint
- production build
- E2E
- 既存CI

実行したコマンド、対象件数、PASS / FAIL を `docs/DEBUG_MATRIX.md` に残します。
「exit 0」だけで完了扱いにせず、実際に何件を検査したか確認します。

## 4. バグ修正ループ

バグを発見した場合は原則として次の順で進めます。

1. 再現する
2. 原因候補を切り分ける
3. 可能なら再現する自動テストを追加する
4. **修正前の状態でそのテストが失敗することを確認する**
5. 原因を特定する
6. 最小限の修正を行う
7. 対象テストを再実行する
8. 全テストを実行する
9. typecheck / lint / production build 等の全体検証を実行する
10. 必要なら実ブラウザー / 実API / 実機確認を行う
11. `docs/DEBUG_MATRIX.md` と `docs/STATUS.md` を更新する

原因不明のまま場当たり的な修正を重ねません。

## 5. シナリオベースの意地悪テスト

各アプリで最低限、次を検討します。

- 何も入力しない
- 空白だけ
- 1件だけ
- 2件だけ
- 非常に多い件数
- 負数、小数、極端に大きい数
- 同じ操作を連打
- 操作途中で条件変更
- 結果表示直後に別画面へ移動
- 戻る / 再読み込み
- 保存後に再起動
- 保存データが欠損、破損、古い形式
- APIが0件
- APIが4xx / 5xx
- APIが遅い
- API応答の項目が欠ける
- 通信途中で失敗
- 外部機能の権限拒否
- 画面幅が狭い
- 長い文字列
- 日本語以外、記号、絵文字を含む入力

仕様上不要な項目は `N/A` として理由を残します。

## 6. バグ記録

最低限、次を残します。

- 概要
- 重要度: Critical / High / Medium / Low
- 再現手順
- 期待結果
- 実際の結果
- 原因
- 修正内容
- 追加した再発防止テスト
- 再確認結果
- 未確認事項

## 7. 自動化

プロジェクトの test / typecheck / lint / build コマンドが固まったら、可能な範囲でGitHub Actions等のCIに載せます。

CIはプロジェクトの技術構成に合わせて作り、雛形から無理に共通コマンドを決めません。
少なくともPR時に「主要テスト + production build」が自動確認できる状態を目標とします。

## 8. 完了条件

原則として次を満たしたときだけ「総合デバッグ完了」とします。

- 主要フローの自動テストがPASS
- 回帰テストがPASS
- typecheck / lint 等、採用している静的検証がPASS
- production buildが成功
- Critical / High の既知未修正バグが0件
- Medium / Low の既知バグは記録済み
- 主要画面幅で致命的なUI崩れがない
- 外部依存の主要成功経路と失敗時挙動を確認、または未確認理由を記録
- 実機が必要な項目を明示
- `docs/DEBUG_MATRIX.md` と `docs/STATUS.md` を更新
- 変更をcommit / pushし、GitHub上に再開可能な状態を残す

## 9. 完了報告の固定形式

総合デバッグの最後は、次の4分類で報告します。

### PASS
確認できた項目、テスト件数、typecheck / lint / build結果。

### 発見して修正したバグ
原因、修正内容、追加した再発防止テスト。

### 未確認項目
実機確認、未網羅の画面や操作など。

### 外部依存などにより確認できなかった項目
API、実環境、権限、営業時間など。

Critical / High の未修正バグが残っている場合は、総合デバッグ完了と表現しません。
