# アイデア受付と担当判定

## 目的

利用者が「いつかやりたい」と思ったことを、実行依頼と混同せずに失わないよう保存する。利用者が実行したくなった時点で、端末の稼働ではなく仕事の性質から担当を決め、適切なクラウドで完了まで進める。

## やりたいこと

現在扱う領域は次の3つである。これは候補一覧ではなく、この基盤を使う目的の範囲とする。

1. **個人用アプリ開発**: 自分で使うアプリを作り、利用後に分かった不便を継続的に改善する。
2. **競馬データ分析**: 取得条件と観測時点が分かるデータを使い、再現可能な加工、検証、比較を行う。
3. **その他の相談案件**: 最初から実装方法を決めず、できることと制約を相談し、実現可能な単位へ具体化する。

最初の稼働案件は **めしルーレットのブラッシュアップ** とする。

| 項目 | 内容 |
| --- | --- |
| 状態 | 実行 |
| 領域 | 個人用アプリ開発 |
| 現在の公開物 | [めしルーレット](https://revise-sato.github.io/meshi-roulette/) |
| やりたいこと | 現在のアプリを使いながら、ブラッシュアップと改善を継続する |
| 担当 | Codex cloud。利用感や優先順位は利用者と相談して決める |
| 最初の完了条件 | 公開画面とソースを取得し、現状の機能、再現手順、改善候補、検証方法を根拠付きで整理する |
| 改善時の原則 | 現物を確認する前に作り直さない。一度に改善テーマを一つ選び、変更前後を別々の実体で検証する |

競馬データ分析は保留資料をそのまま実装仕様とせず、再開時に目的、利用可能なデータ、評価方法を確認してから `実行` に移す。その他の相談案件は、相談内容から成果物と完了条件を仮置きできるまでは `メモ` とする。

## 正本と状態

アイデアメモの正本は、Google Driveルート直下のGoogleスプレッドシート `Tottoko` とする。1件を1行で管理し、GitHubには運用手順だけを置く。`Tottoko` はアイデア台帳であり、画像・動画・実データ等を置くフォルダではない。コードや仕様の正本は各GitHubリポジトリとする。

判断上の状態は次の3つとし、`Tottoko` の「状態」列には対応する値を記録する。

- `メモ`: 保存したが、着手は約束していない。シートでは `未処理` または `保留`。
- `実行`: 利用者がやりたいと表明し、担当と完了条件を決めた。シートでは `対応中`。
- `完了`: 完了条件を検証した。成果物の保存先を記録し、シートでは `完了`。

## 受付手順

利用者が思いつきを伝えたら、`Tottoko` に1行追加する。IDは既存の `TT-nnnn` の連番を使い、内容が不足していても仮置きできる欄はメモに残し、質問のために保存を止めない。

```text
ID: 次の未使用 TT-nnnn
登録日時: YYYY-MM-DD HH:mm（Asia/Tokyo）
内容: 利用者の言葉を意味が変わらない長さで要約
プロジェクト: 関連する既存Repo・案件。未定なら「未定」
種類: アイデア／課題／やること／候補
状態: 未処理
更新日時: 登録日時と同じ値
メモ: きっかけ、完了の姿、関連資料URL、担当、判定理由（分かる範囲で記入）
```

保存した時点では調査、実装、外部送信を始めない。「メモして」に実行の意味を含めないためである。会話内でDriveへ書き込めない場合は、上の書式で貼り付け可能なメモを返し、未保存であることを明記する。

## 実行時の担当判定

利用者がアイデアを「やりたい」と表明したら、成果物と完了条件を先に1文で定め、`Tottoko` の対象行を `対応中` に更新してから、次の順序で担当を判定する。

1. リポジトリ内のコード、設定、テスト、CLI、データ処理、再現可能な成果物を作る仕事は **Codex cloud** が担当する。GitHubを正本にし、依存関係復元、自己診断、テストまでを完了条件に含める。
2. 最新情報の調査、複数資料の継続観測、通知、定期実行は **ChatGPT Work Cloud** が担当する。PCの稼働を前提にせず、調査結果や監視条件はGoogle Driveへ残す。
3. 外部送信、公開、購入、インストール、既存原本の上書き、認証や承認は **人の操作** とする。実行前に対象と影響を示して確認を得る。

複合案件は一つの担当へ無理に寄せない。たとえば「市場を毎週調べ、その結果を処理するCLIを作る」なら、Work Cloudが調査・定期実行、Codex cloudがCLI実装、人が公開を承認する。アイデアメモの`担当`にはこの受け渡し順を1行で書き、各工程に個別の完了条件を付ける。どの工程にも属さない作業を残さない。

## 判定例

| やりたいこと | 担当 | 判定理由 |
| --- | --- | --- |
| CSVを検査するコマンドを追加する | Codex cloud | コード、テスト、再現可能な処理を変更するため |
| 競合サービスの更新を毎週確認する | ChatGPT Work Cloud | 最新情報の継続調査と定期実行であるため |
| 調査結果を公開サイトへ投稿する | 人の操作 | 外部公開は実行前の承認が必要なため |
| 更新を監視し、変化を集計するコードを作る | Work Cloud → Codex cloud | 監視と実装を分け、それぞれの正本と検証方法を保つため |

## 実行へ移す手順

1. `Tottoko` の対象行を開き、利用者が示したアイデアと同一か確認する。
2. 状態を `対応中` にし、担当、判定理由、完了の姿を「メモ」列に記録する。
3. コードが必要な場合は対応するGitHubリポジトリを決める。画像・動画・Sheets・実データは、用途に合う既存Drive領域へ置き、必要なら保存先URLをメモに記録する。
4. 担当ごとの工程を実行し、成果物が変わったことと目的を満たしたことを検証する。
5. 成果物の保存先と検証結果をメモへ記録し、全工程を満たした場合だけ状態を `完了` にする。
